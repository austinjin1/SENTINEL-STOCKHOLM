## The four decisions

- **1_N2**: Confirm 'descriptive, p = 1' for both N2 endpoints; keep gate G-D1b for N2 exactly as stamped (both endpoints, against every comparator, no-go final for the track). Reason: Q5, Q6, rulings §2.2 and amendment §9 give this result mechanically (G_eff 7.94 and 7.90 on all stations with the variable; floors are never lowered; the family of 2 is never shrunk). The stamped G-D1b text has no exemption for descriptive endpoints, and dropping it would lower a bar after the metadata were seen. The realised-cell check cannot promote an endpoint.
- **2_pin_change**: Accept with conditions (F5): last line wins and earlier states become invalid; changed_under_stamp, deviations sha256 and stamp row id in every run record and registry row; each line is a counted configuration and names the runs that are repeated; lines for sites.py, the reserved modules, gso_mt/data.py, constants.py and pins.json#values need the lead's read of the diff; F1 ruling in force. Reason: Without a route the D2 entry or a lever edit of sites.py blocks every entry point; the route is line-exact, works only in the stamped state and has no path for tables, split, role tables or pool fingerprints. As coded it lets a file alternate between stamped states, covers the guard and role modules, and does not record the change in any run record although the entry says so.
- **3_scan_cube**: Accept the run-time substitution; no lever-loader parameter needed now. Reason: It only tightens (filter inside the scan, reserved-site assertion, error on a later row), is restored in a finally block, covers every load_cube call of the lever loader, and its output is pinned by the pool fingerprint. Conditions: reader named in the run record; fingerprint check mandatory. Real-data equality with the frozen reader was not checked by me.
- **4_pin_code**: Yes: pin driver, trainer, net, criterion, gates, GBM and stack code by file in a second read-only pin record before the first non-smoke fit, verified by every entry point and written to every run record; this does not need a new entry before the stamp. Reason: §2.1 is consistent with the letter of rulings §2.3, but no run record carries a usable code hash (only a whole-package hash that changes with any workstream's edit), there is no git history, and the unpinned code, including the guard's own file, changed three times during this review. References and D1 are compared on inner numbers; they must be shown to share one code state.
